## vault

> 信息总是会失败的。消失或者无法被知晓。Vault容纳所有的信息，在计算机中，信息总是以文件格式和文件中的内容体现的。文件格式意味着解码方式，而文件内容则是真正的信息所在。

## 结构

vault 不预设结构。但是，完全无结构意味着熵的快速增长。这里给出方案：

1. 日期
按照日期，每日创建新文件夹，命名为 “xxxx-xx-xx”

2. 格式
给相同格式的文件创建文件夹，如“pdf/” “md/”

3. 类型
如“日记”，“bilibili切片”等

4. 其他

虽然给出了上述的预设，但是并不意味这他们是互斥的。一个vault完全可以由日记结构为预设，其中包含格式或类型结构。当然，vault的格式应当在根目录的AGENTS.md中声明。

一般来说，vault接受所有的信息，这就意味着其本身可能无比混乱。用户当然可以把自己的项目都放进其中，尽管这不是推荐的做法。但是，在维持了一定的结构后，在初步读取时不会那么麻烦

## 更改

vault中的内容并非不可更改。但是，是否能够更改需要看wiki中的记录，这会在下一章节详细讲解。如何更改，也需要wiki的规范。

## 插件规范（草案）

> 承接上文的 test 布局，展开为通用规则。正式协议文档将来立稿于 `.meta/docs/`，本节是底稿。

### PLUGIN.yaml：注册清单

- `name` — 插件唯一标识。全局唯一
- `description` — 简短描述
- `version` — 单调可比较即可；破坏性变更升主版本
- `scopes` — 写权限域声明（见下）；空列表 = 只读插件
- `depends` — 依赖的插件 id 列表（规则见「依赖」）
- `updated` — 最后更新日期
- `entry` — 入口指针：`doc` 逻辑本体（必填），`scripts` 工具列表（可选）


### PLUGIN.md：逻辑本体

正文结构：职责（管什么）→ 流程（怎么做）→ 不变量（必须维持什么）→ 依赖 → 合规自检 → 变更记录。技能薄壳只负责触发与路由，第一步永远是读对应 PLUGIN.md——文档先行，技能即薄壳。

3. 数据公约（frontmatter 链接字段等跨实例可读的最小格式约定）在协议层全体共享，不构成依赖；`depends` 只声明行为复用

5. 硬方向：通用插件不得依赖个性化插件——骨架与实例分离在依赖图上的形状
6. 承重件不依赖任何插件（分层的底）
7. 卸载被依赖者：自检报 error 阻断，除非显式声明级联

### 生命周期

- **装**：目录就位 → manifest 合法 → 登记（宪法指针 / registry）→ 自检通过
- **升**：版本号 + 变更记录各一行；破坏性变更升主版本，并提示依赖方
- **卸**：注销登记 → 归档。任何装卸操作前必须先跑通自检插件

### 合规检查

三级检查、三个时机、两级判定：

| 级别 | 查什么 | 谁执行 |
|---|---|---|
| 静态结构 | manifest 字段齐全、id 唯一且与目录一致、entry 指向存在、依赖无环且方向合法 | 脚本 |
| 行为痕迹 | 产出落在声明 scope 内、承重件在位（「拔了会响」在这里响） | lint 型插件 |
| 流程冒烟 | 新会话 agent 按技能路由 → 读 PLUGIN.md → 对测试资产完整走一遍 | agent 实测 |

时机：装卸时（强制）、健康检查时（定期）、迁移/回填时（跨实例校验）。
判定：error（承重缺失、scope 越界、注册不一致）阻断操作；warning（版本过期等）仅提示。

检查者本身也是插件（自举）：自检插件 `class: bearing`，装卸任何插件前必须先跑通它。

### 协议管什么、不管什么

- **管**：插座的形状——manifest 字段、scope 分类、注册与发现、生命周期、冲突裁决、数据链接字段
- **不管**：插头里装什么——怎么摘要、怎么索引、日记怎么组织，全是插件内容
- 判据：两个实例、两个插件之间需要共享的，进协议；单个插件内部怎么干活的，不进
